# ADR-0039: Owner-owned archive and audit triggers

Status: Accepted (owner 2026-10-29) · Date: 2026-10-18

## Context

ADR-0038's residual risks: anyone who can run SQL with the app's database credential (a leak, code execution in the Worker, a future injection) can delete whole organizations, since the foreign-key cascades also remove projects and billing records the role has no `DELETE` on. They can also take over accounts and tenants by writing auth tables: a password hash, an email, a role, a membership, a session's user or a password-reset row. The database can't tell that actor from the app (the inputs a check would read are writable by the same role), so no database-side authorization fixes either risk. Recovery today is Neon's 6-hour restore window, the daily snapshots and the 30-day dumps (ADR-0036), all of which roll back the whole database.

The 2026-10-18 research (owner's local `ADR38-residual-risks-results.md` §2.4 B, §3.5 B) verified that the runtime role can't disable triggers, set `session_replication_role` or truncate. So triggers installed by the owner fire for it. A prototype also showed that an owner-owned archive captures a cascaded delete and stays out of the runtime role's reach.

Owner decisions (2026-10-18): keep self-service organization deletion; no deletion cap; no separate auth credential; add archive/audit triggers before real customer data. Design choices made at the start of this work: record every session insert and delete; keep 90 days with an owner-run purge; audit password, email, membership and password-reset writes, including membership moves to another user or organization; archive `user` and `account` deletes too.

## Decision

1. **An owner-owned schema `archive`**, created by migration `0006_archive_audit` (the `verification` audit changed by `0007_hashed_verification`, decision 8) as the migration role (`app_owner`). `REVOKE ALL … FROM PUBLIC` on the schema, its two tables and its two functions; `app_runtime` gets no privilege on any of them (no `GRANTS` entry: `database-role.test.ts` lists `public` only and asserts that the archive is unreachable).
2. **`archive.deleted_row`: a copy of every deleted row** of `organization`, `member`, `invitation`, `project`, `billing_subscription`, `user` and `account`. It's written by an `AFTER DELETE … FOR EACH ROW` trigger `archive_delete` calling `archive.capture_delete()`. Columns: `at`, `txid`, `db_user` (`session_user`), `table_name`, `organization_id` (the row's own, or its `id` for `organization`) and `row_data` (`to_jsonb` of the old row). Before storing, it removes the keys `password`, `access_token`, `refresh_token` and `id_token`, so an archived account holds no hash or token. FK cascades fire the child tables' triggers, so one organization delete archives the organization and every cascaded row in the same transaction. Every table with an `organization_id` column must carry the trigger; a catalog test fails for a new tenant table without it.
3. **`archive.auth_event`: access-granting auth writes**, from `archive.audit_auth()`:

   | Event                              | Fires on                                                             | Recorded (`detail`)                                                                                                                                                              |
   | ---------------------------------- | -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
   | `session.insert`, `session.delete` | every sign-in, sign-out, revocation, expiry cleanup                  | session id, **sha256 of the token** (never the token)                                                                                                                            |
   | `session.update`                   | only when `id`, `user_id` or `token` changes                         | as above, plus the previous id and token fingerprint                                                                                                                             |
   | `account.insert`, `account.update` | insert; update of `password`, `user_id`, `provider_id`, `account_id` | provider, account id, `password_set`, `password_changed` (flags, never the hash)                                                                                                 |
   | `user.update`                      | `email` (or `id`) changes                                            | old and new email                                                                                                                                                                |
   | `member.insert`, `member.update`   | insert; update of `role`, `user_id`, `organization_id`               | member id, role, previous role and organization                                                                                                                                  |
   | `verification.insert`, `.update`   | every insert; updates of id, identifier, value or expiry             | verification id, expiry (and the previous ones), `identifier_changed`, `value_changed` (flags). Never the identifier or the value; `user_id` is the user the value names, if any |

   Every event also stores `user_id`, `previous_user_id` (updates), `organization_id`, `at`, `txid` and `db_user`. Routine session refreshes (`expires_at`, `updated_at`, `ip_address`, `user_agent`, `active_organization_id`) record nothing; `WHEN` clauses skip those updates. A delete of a session followed by re-inserting its token for another user shows up as a `session.delete` and a `session.insert` with the same fingerprint. The fingerprint is a SHA-256 of a random 32-character token. It can't be turned back into the token, and the token alone can't sign anyone in, since the cookie is signed with `BETTER_AUTH_SECRET`. It exists only to link those two events.

4. **Trigger functions are `SECURITY DEFINER` with `search_path = pg_catalog, pg_temp`** and fully qualified names, so neither a temporary table nor anything on the caller's search path can divert the copy (tested). They run as their owner, so the runtime role needs no grant to fire them, and attribution comes from `session_user`, which `SECURITY DEFINER` doesn't change.
5. **Retention: 90 days**, longer than the 30-day dumps (ADR-0023), so damage noticed late can still be restored row by row. The archive holds personal data (emails, names in `user`, `invitation`, `auth_event`): ADR-0015's rules apply. The owner reads it only in the Neon SQL Editor, never copies it into logs, tickets or chat, and purges it by hand (runbook "Archive and audit"): monthly, and at once for a data-deletion request, which must also cover the archive. No scheduler is added; a missed purge only keeps rows longer. The dumps include the `archive` schema, so purged rows survive in dumps up to 30 days more (ADR-0023 allows deleting a dump early).
6. **Restore** is an owner operation in the SQL Editor: `jsonb_populate_record(NULL::public.<table>, row_data)` inserts of the rows from **that deletion's transaction** (`txid`) only, so members, invitations and projects removed earlier don't come back, in one transaction, parents first (organization, member, invitation, project, billing_subscription); then re-check billing against Polar (runbook). A restored account has no password: the user resets it. A test restores an organization deleted through the app and gets the same rows back, without an admin removed before the deletion.
7. **The migration has no SQL comments.** `pr-title.yml` treats any comment other than drizzle-kit's `--> statement-breakpoint` as a possible contract migration (ADR-0029 decision 7), so the explanations live here. Every statement is idempotent (`IF NOT EXISTS`, `CREATE OR REPLACE`), so the migration can be re-applied after a `--no-acl` restore to bring back its `REVOKE`s. drizzle-kit doesn't see the schema: `db:generate` diffs `src/schema` against its snapshots, never the database (checked: no changes after 0006).

8. **Password-reset identifiers are stored hashed** (`0007_hashed_verification`, 2026-10-19). Better Auth's `verification.storeIdentifier: 'hashed'` stores the unpadded base64url SHA-256 of `reset-password:<token>`, so a reader of `verification` gets no usable reset link. A stored hash used as the token is refused: Better Auth hashes it again, and its plaintext fallback looks up `reset-password:<hash>`, which a stored hash (no `:`) never equals. Rows stored in plaintext before the switch still work, once, until they expire (at most an hour). A hashed row can't be told apart from any other `verification` row by its identifier, so the `reset-password:` prefix condition was dropped and **every** `verification` insert is audited; a reset row planted with SQL is recorded whatever its identifier. Attribution assumptions:
   - `user_id` (and `previous_user_id`) is set only when the row's `value` equals the id of an existing `user` (an exact lookup inside the trigger, never a pattern). That holds for password resets, and for Better Auth's account-deletion and unproven-account cleanup rows, should those flows be enabled. It never decides whether a row is audited.
   - The `value` is never copied: other flows keep secrets there (an email or phone OTP, OAuth state with the PKCE verifier), and a row whose value is no user id is recorded with `user_id` null. A future flow whose value is another user's id would be attributed to that user; check this before enabling a plugin that writes `verification`.
   - Events no longer say which flow wrote the row (the 0006 `kind: 'reset-password'` key remains on older rows only). Today password resets are the only `verification` rows (email verification uses signed JWTs; no social sign-in, magic link or OTP), so every `verification.insert` is a reset request until a flow is added.

## Limits (stated, not solved)

- **It protects against `app_runtime`, not the owner.** `app_owner` can read, change, purge or drop the archive and disable the triggers. Production ran as `app_owner` until 2026-10-29: until then the archive recorded deletes and auth writes made through the app, attributed to `app_owner`, and anyone holding the production credential could erase it. Since the switch (ADR-0038 G1–G4 passed), the app's production credential is `app_runtime`, which has no privilege on the archive; the owner credential (migrations, backups) still can.
- **`db_user` is a database login, not a person.** Every request from the app shows as the runtime role. The rows show what was written and when, not who asked.
- **It's written in the same transaction.** A rolled-back attempt leaves nothing, by design. A committed attack can't remove its own rows without the owner's privileges.
- **It records; it doesn't prevent.** No delete or write is refused (the cap was rejected: anyone could use it to block legitimate deletions). Nothing alerts on new rows yet; reading them is part of an investigation or a periodic owner review.
- **Not a backup.** It lives in the same database: losing the database or a full rollback takes the archive with it. ADR-0036's objectives are unchanged.
- **Coverage is per table and column.** Writes outside the table above aren't recorded (for example `organization` renames, `invitation` changes, `rate_limit`, `verification` deletes (consumption and expiry cleanup), `user.email_verified`).
- **Cost:** one extra insert per deleted row, per session created or deleted, and per audited write, in the same transaction. Sign-in and sign-out each gain one row.

## Consequences

- **Adding a tenant table** (AGENTS.md recipe) also means adding the `archive_delete` trigger in a migration; the catalog test in `apps/app/test/archive.test.ts` fails without it.
- **New access-granting auth columns** (for example two-factor secrets) need a decision on auditing, recorded here.
- **Restores:** after a `--no-acl` restore, re-apply `0006_archive_audit.sql` and then `0007_hashed_verification.sql` as the owner, with `0005` (runbook "Runtime role" → After a restore; a database older than the code version runs that version's migrator first, procedure (b)). `0007` replaces `audit_auth()` and the `verification` triggers and revokes `DELETE` on `account` again.
- **Removing** a trigger or the schema is a contract migration (`!` in the PR title) and needs a superseding ADR.

## Alternatives

- **Accept and rely on backups** (status quo): every recovery is a full rollback, and nothing records an auth-table takeover.
- **pgAudit:** available only on Neon's HIPAA projects (R06).
- **Application-level audit log:** misses exactly the threat here (SQL with the runtime credential bypasses the app).
- **A deletion cap, soft delete, owner-only deletion, RLS or a definer function guarding deletes:** rejected or not chosen in the 2026-10-18 research (ADR-0038 Notes): a global cap is a denial-of-service lever, soft delete conflicts with Better Auth's hard deletes, owner-only deletion removes self-service, and database-side checks read data the same role can write.
- **Recording identity changes only for sessions** (with a table of deleted-token fingerprints): fewer rows but more logic and edge cases; the owner chose full insert/delete coverage.

## Notes

- 2026-10-18, verified locally (Postgres 17, `app_test`, as `app_runtime` and the local owner): `apps/app/test/archive.test.ts`, `database-role.test.ts` (archive unreachable, triggers can't be disabled, replaced or removed, `session_replication_role` refused) and `organization-delete.test.ts` (the HTTP delete archives every cascaded row in one transaction, as the runtime role and as the owner; a rolled-back delete archives nothing). Dropping two of the triggers failed 8 tests. A `pg_dump` / `pg_restore --no-owner --no-acl` round trip kept the schema, triggers and rows. Not yet verified through Hyperdrive or on Neon: `session_user` through Hyperdrive is expected to be the configured user (ADR-0038 Notes).
- 2026-10-19, owner decision: **keep the session-token fingerprint** (`token_sha256`, decision 3). Purpose: it's the only link between a `session.delete` and a `session.insert` of the same token for another user, the takeover pattern the research asked to detect; without it they could only be correlated by time. Assumptions, checked in Better Auth 1.7.7: tokens are `generateId(32)` (32 characters from 62, `crypto.getRandomValues` with rejection sampling: about 190 bits), and our config doesn't override token generation. A SHA-256 of such a token can't be reversed or guessed, and it isn't a credential: Better Auth looks sessions up by the token itself, behind a cookie signed with `BETTER_AUTH_SECRET`. Only the fingerprint is archived, never the token (`archive.test.ts`). Access is the archive's (decision 1: owner only, no runtime privilege). Retention: it's personal data linked to `user_id`, kept and purged with the rest of `auth_event` (90 days, data-deletion requests included; dumps up to 30 days more).
- 2026-10-19, verified locally: hashed reset identifiers (`email.test.ts`: stored form, stored hash refused as a token, plaintext row accepted once, expired hashed and plaintext tokens refused, single use) and the 0007 audit (`archive.test.ts`: reset request, planted row, value that names no user, expiry revival and identifier swap).
- 2026-10-29, accepted by the owner. Evidence: migration `0006_archive_audit` (and `0007`) shipped with app 0.4.0 (`c8d6a2a`, released 2026-10-29); since the ADR-0038 switch the same day, production writes as `app_runtime`, which has no privilege on the archive (runbook "Runtime role (ADR-0038)" record, `docs/runbooks/README.md`). The limits above still apply.
- 2026-10-31, ADR-0044: `purge_deleted_account` runs this ADR's data-deletion statements after deleting the user, so they also erase what `archive_delete` just copied. The tombstone's `user.update` event keeps the old email until then.
