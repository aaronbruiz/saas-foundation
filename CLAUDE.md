## Claude Code (implementer)

- You implement; Codex reviews independently in a separate tree. Never self-approve.
- Loop: implement → `pnpm check` + `pnpm test` + `pnpm test:e2e` → hand off for review (Codex runs `$review-pr` in a detached worktree, ADR-0042) → apply only the review findings (narrow corrections) → re-review.
- Commit locally and run the Codex review on the local branch first; push once, when the review is clean. Every push to a PR re-runs CI, the title check and the preview (a fresh Neon branch reset and redeploy).
- Don't widen a PR beyond its task; propose follow-ups instead.
- One session or subagent owns a branch and its worktree; a coordinating session owns its workers (`coordinate`). The task's brief records path and branch, and the head comes from Git. Don't edit, reset or remove a worktree or branch you can't show is yours (`git worktree list`, the brief); ask the owner. Migrations, generated files and test runs are one session's or worker's at a time. Tests run through `scripts/test-lock.sh test|e2e`, manual runs too: `app_test` and port 3000 are shared by every clone on the machine.
- On resuming, `git fetch origin`, then read Git (`git status`, `git log`, `git worktree list`), the PR (`gh pr view <n> --json state,headRefOid,body`) and its CI runs before trusting the brief or handoff, and correct them where they differ. A handoff or an agent's summary is a claim, not state.
- Before asking the owner to merge, `git fetch origin main` and report what the evidence covers, review and tests separately: `head <sha>; base <sha>; review <result file> at <head>/<base>; CI <run id> tested <sha> (parents <head>, <base>); main <sha>; governance: <files or none, list in `review-pr`>; description edits after approval: <n>`. A PR's CI run tests GitHub's merge commit, not the head: read it from the checkout log (`gh run view <id> --log | grep 'HEAD is now at'`). Then, separately, whether `main` moved past the PR's base (`git merge-base --is-ancestor origin/main <head>` fails). If it did, compare the current head and `origin/main` with the revisions each piece of evidence saw before calling it stale: a CI run whose merge commit's parents are the current head and `origin/main` already tested the combination; a review saw only its own head and base. For evidence that didn't see the current pair, list the commits `main` gained since its base (`git log --oneline <base>..origin/main`, with the files they touch) for the owner to decide between rerunning (merge `main` in, ADR-0030) and merging as is, or rerun it, or report it as not rerun. When only `main` moved, `coordinate`'s base-update step defines this for the PR about to merge.
- The owner merges only with `gh pr merge --squash --match-head-commit <head from the evidence line>`.
